## 1. 실행 전에 준비할 것

백엔드는 JDK 21, 실행 중인 MySQL, `cuty` 데이터베이스가 필요하다. 환경변수에는 실제 로컬 값을 넣고 비밀번호나 JWT secret을 문서와 Git에 남기지 않는다.

백엔드 저장소 `mr-world-cuty-server`에서 다음 환경변수를 준비한다.

```text
DB_URL=jdbc:mysql://localhost:3306/cuty
DB_USERNAME=로컬_MySQL_계정
DB_PASSWORD=로컬_MySQL_비밀번호
JWT_SECRET=충분히_긴_로컬_테스트용_문자열
```

프론트엔드 저장소의 `.env.local`에는 다음 한 줄을 둔다.

```text
VITE_API_BASE_URL=http://localhost:8080/api/v1
```

음성 기능을 함께 보지 않는다면 `VITE_VOICE_API_BASE_URL`은 이번 확인에 필요하지 않다.

빈 데이터베이스에서는 고객 화면에 상품이 나오지 않는다. 먼저 미래 출발일의 `RECRUITING` 상품이 하나 이상 있어야 한다. 기존 로컬 테스트 DB를 사용하거나, 백엔드 Swagger UI의 직원용 `POST /api/v1/staff/tours`로 상품을 준비한다. Swagger UI는 `http://localhost:8080/swagger-ui/index.html`에서 연다.

## 2. 서버와 화면 띄우기

터미널을 두 개 열어 각각 실행한다.

백엔드:

```bash
cd ../mr-world-cuty-server
./gradlew bootRun
```

프론트엔드:

```bash
npm ci
npm run dev
```

프론트 터미널에 표시된 `Local` 주소를 브라우저에서 연다. 기본값은 `http://localhost:5173`이며, 포트가 이미 사용 중이면 터미널에 표시된 다른 주소를 사용한다.

실행 확인:

- `http://localhost:8080/swagger-ui/index.html`이 열리면 백엔드가 실행 중이다.
- 프론트 홈이 열리면 프론트가 실행 중이다.
- 로그인이나 상품 조회 때 `Failed to fetch`, `Network Error`가 보이면 두 서버의 실행 상태와 `.env.local`을 먼저 확인한다.

## 3. 실제 고객 계정으로 확인하기

1. 프론트에서 `회원가입`으로 이동한다.
2. `고객` 유형에서 테스트용 계정을 만든다. 연락처는 화면에서 하이픈을 입력해도 서버에는 숫자만 전송된다.
3. 가입한 계정으로 로그인한다.
4. `고객 시연 모드`를 누르지 않고 `여행상품`으로 이동한다.

정상이라면 서버의 모집 중 상품이 표시된다. 실제 로그인 세션에서는 남아 있던 DEMO 상태보다 서버 세션이 우선하며, 로그인 성공 시 DEMO 개인정보도 정리된다.

## 4. 핵심 흐름을 눈으로 확인하기

### 상품 → 서버 Quote

1. 상품 카드를 열고 `구성 시작`으로 이동한다.
2. 등급·호텔·교통·식사·음료를 바꾼다.
3. 신청·결제 화면으로 이동한다.

정상 표시:

- 신청·결제 화면에 `서버가 계산한 금액`과 할인율이 나온다.
- 아직 예약을 만들지 않았으므로 제목은 `선택한 구성으로 예약할까요?`다.
- 동의 체크 후 `PENDING 예약 생성` 버튼을 누를 수 있다.

### PENDING 생성과 새로고침 복원

1. 동의 체크 후 `PENDING 예약 생성`을 누른다.
2. 주소창 URL을 확인한다.
3. 그 상태에서 브라우저를 새로고침한다.

정상 표시:

- 제목이 `PENDING 예약이 생성됐어요.`로 바뀐다.
- 화면에 서버가 발급한 예약번호가 표시된다.
- URL에 `?booking=예약번호`가 남는다.
- 새로고침 뒤에도 같은 예약번호와 Mock 카드 결제 화면이 복원된다.

### 결제 거절 → 재시도 → 승인

1. Mock 카드번호에 `2`처럼 `1`이 아닌 값을 넣고 `Mock 결제 요청`을 누른다.
2. 같은 화면에서 카드번호를 `1`로 바꾸고 다시 요청한다.

정상 표시:

- 첫 요청은 `FAILED`로 표시되고, 예약은 `PENDING` 상태로 남는다.
- 실패 뒤에도 같은 예약번호로 다시 결제할 수 있다.
- 카드번호 `1`은 `SUCCESS`가 되고 예약 상세 화면으로 이동한다.
- 상세 화면에서 예약은 `결제 완료`, 결제는 `결제 성공`으로 표시된다.

실제 카드번호는 입력하지 않는다. 이 화면은 서버 Mock 결제만 호출한다.

### 예약 목록에서 결제 이어가기

승인 테스트와 별도로 새 PENDING 예약을 하나 만든 뒤 결제하지 않고 다음을 확인한다.

1. `내 여행` → `신청한 여행`으로 이동한다.
2. `결제 전` 상태의 카드를 연다.
3. 상세 화면의 `결제 계속하기`를 누른다.

정상 표시:

- 예약 목록에 서버 예약번호와 `결제 전` 상태가 표시된다.
- 상세에서 `결제 계속하기`가 보인다.
- 결제 화면 URL에 같은 `booking` 값이 유지되고, 새 예약을 만들지 않고 기존 PENDING을 불러온다.

### PENDING 옵션 수정

1. PENDING 결제 화면에서 `구성 수정하기`를 누른다.
2. 옵션을 하나 바꾸고 다시 신청·결제 화면으로 이동한다.
3. `현재 구성으로 PENDING 예약 수정`을 누른다.

정상 표시:

- 기존 예약과 현재 구성이 다를 때 바로 결제할 수 없다는 안내가 나온다.
- 수정 버튼을 누른 뒤 같은 예약번호가 유지된다.
- 서버 계산 금액이 바뀐 구성 기준으로 갱신되고 결제 버튼이 다시 활성화된다.

### 예약 취소와 환불 상태

1. 카드번호 `1`로 결제한 예약의 상세 화면을 연다.
2. `예약 취소` → `예약 취소 확인`을 누른다.

정상 표시:

- 예약 상태가 `예약 취소`로 바뀐다.
- 성공 결제가 있었다면 결제 상태가 `환불 완료`로 바뀐다.
- 취소된 예약에서는 취소 버튼이 비활성화된다.

## 5. 최근 보완 항목 회귀 확인

- 실제 고객 로그인 뒤 상품 목록이 샘플 4개가 아니라 서버 상품으로 보이는가.
- 서버 상품을 장바구니에 담고 새로고침해도 다시 조회되어 카드가 보이는가.
- 서버 상품 구성을 저장하고 `내 여행` → `저장한 구성`에서 `이어서 구성`이 가능한가.
- PENDING 결제 URL을 복사해 같은 로그인 세션에서 다시 열어도 예약이 복원되는가.
- 예약 목록과 상세에서 같은 예약번호·금액·상태가 보이는가.
- 만료되거나 잘못된 인증 상태에서 보호 API가 401을 반환하면 가짜 로그인 상태에 머물지 않고 로그인 화면으로 돌아갈 수 있는가.

## 6. 화면이 다르면 먼저 볼 곳

| 보이는 현상 | 우선 확인 |
| --- | --- |
| 상품 목록이 비어 있음 | DB에 미래 출발일의 모집 중 상품이 있는지 확인 |
| DEMO 배지가 보임 | 로그아웃 후 실제 계정으로 다시 로그인하고 DEMO 버튼을 누르지 않았는지 확인 |
| 로그인부터 실패함 | 백엔드 실행, `.env.local`, API 기본 URL 확인 |
| Quote 또는 예약 생성 실패 | 상품 시작일이 출발 7일 전 마감을 지나지 않았는지 확인 |
| 결제가 계속 거절됨 | Mock 카드번호가 정확히 `1`인지 확인 |
| 새로고침 후 예약을 못 찾음 | URL의 `booking` 값, 로그인 계정, 해당 예약 소유자 일치 여부 확인 |
| 옵션 수정 후 결제 버튼이 꺼져 있음 | `현재 구성으로 PENDING 예약 수정`을 먼저 눌렀는지 확인 |

## 7. 테스트를 마친 뒤 기록할 형식

다음 형식으로 `docs/api-integration-progress.md` 작업 로그에 덧붙인다.

```text
### YYYY-MM-DD — 고객 API 브라우저 재검증

- 환경: 프론트 커밋 / 백엔드 커밋 / 브라우저
- 확인: 로그인 → 상품 → Quote → PENDING → 결제 실패 → 재시도 성공
- 확인: 새로고침 복원 / 예약 목록 재진입 / PENDING 옵션 수정 / 취소·환불
- 미확인: 실제로 실행하지 못한 항목
- 오류: 없음 또는 재현 경로와 화면 문구
```

`npm run build`와 `npm run lint` 통과는 코드 검증이고, 위 브라우저 시나리오를 실제로 실행했다는 뜻은 아니다. 두 결과를 구분해서 기록한다.
